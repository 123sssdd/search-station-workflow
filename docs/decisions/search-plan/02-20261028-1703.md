# Brainstorm 02 评审：每轮搜索执行方案模板 v0（01-20261028-1705）
结论：方向对，第 0 步按领域定标准是亮点。但写死的数量和时长容易让人凑数，前 3 条必改。

1. 【必改】下限改成“按饱和度结束”，不靠硬凑。小众领域可能根本没有 100 条。
   建议：100–200、≥30 组关键词、≥45 分钟保留为默认目标；结束条件加一条“饱和”：最后 5 组关键词带来的新增去重结果少于 10%。
   达到饱和但没到数量下限时，可以写饱和证据（每组关键词的命中数）申请结束，由非开轮方 BrainStorm 批准。
   “单轮不少于 45 分钟”只是过程指标，不要放进准出门槛。
2. 【必改】第 0 步要防止自说自话。每个评价维度至少要有 2 个互相独立的来源；只有一个来源的标「弱」，权重减半。
   质量评估复核标准时，要标出哪些阈值是推断出来的、哪些是来源原文。
3. 【必改】评论区读取要和平台规则对齐。小红书属于“只读、低频”渠道：每条最多读 10 条评论，每轮读评论的笔记不超过 20 篇，遇到风控就停下，按 B 类报告。
   GitHub 用 issues 和最近的 commit 代替评论区，B 站等平台按同样的上限处理。
4. 标准缓存：standards 存进 decisions/standards/<领域>.md，30 天内同领域直接复用（第 0 步只补增量），省掉每轮 15–30 分钟和 Firecrawl 积分。
5. 第 3 轮抽检写成“非开轮方 BrainStorm 抽检 20%”，和 v2 的“另一方复核”口径保持一致。抽检时优先抽分数在门槛附近 ±1 分的条目。
6. 方案确认加超时：Searcher 提交 plan 后，开轮方 15 分钟内没回复就视为通过。夜间执行属于 A 类，可以直接跑。
7. 进度汇报：每 30 分钟只发给开轮方，用 priority:false，内容只写“条数、去重数、关键词执行率、饱和度”，不打扰其他 bot。
8. 第 1 步的入选数 10–20 条，给用户看的清单建议只放前 10，其余放进附录，免得清单太长没人看。

同意把它作为 Searcher 和质量评估的 B 类指令变更，先交用户拍板。
