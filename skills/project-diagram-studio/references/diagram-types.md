# 编程项目图型指南

先选择要回答的问题，再选择图型。浅色手绘风统一配色、图标、描边和字体，不改变各图型的语义。
用户指定的图型、用途、比例或新样式优先；本文件中的排版是起点，不是固定模板。
只读取当前需要的图型小节。遇到未列出的图型，采用该图型的常规规范，不强行改成流程图。

## 快速选型

| 读者要知道什么 | 图型 |
| --- | --- |
| 系统由什么组成，组件如何协作 | `architecture` 架构图 |
| 一次请求中谁先调用谁，如何返回 | `sequence` 时序图 |
| 任务按什么步骤和条件推进 | `flowchart` 流程图 |
| 数据从哪里来，怎样变换，流向哪里 | `dataflow` 数据流图 |
| 数据实体之间是什么关系 | `er` 实体关系图 |
| 一个对象如何改变状态 | `state` 状态图 |
| 服务实际运行在哪里，网络如何连接 | `deployment` 部署图 |
| 代码模块、类或包之间如何依赖 | `module` 模块或类图 |
| Agent、模型训练或评测怎样协作 | `ai-pipeline` AI 工作流 |
| 用户跨页面如何完成任务 | `ui-flow` 页面与交互流程 |
| 性能、质量、成本或方案差异如何比较 | `metric/comparison` 数据或对比图 |

同一项目可用多张互补图解释；一张图先解决一个主要问题。信息过密时拆图，不靠缩小文字容纳。
不必每张图都带分层主体、右侧服务栏和底部机制图；这些只适合部分架构介绍图。

## 通用语义约定

- 为关系先定义动词：调用、发布、读写、依赖、包含、继承或状态迁移；箭头不能只表示“有关”。
- 实线与虚线的意义按图型定义并放入图例。例如时序图虚线可表示返回，部署图虚线可表示边界。
- “待实现/可选”优先使用明确标签、独立区域或角标；不要让虚线同时承担两种含义。
- 色彩辅助识别角色或阶段，不能独自承担通过/失败、同步/异步等重要区别。
- 名称、箭头起终点、条件和终止规则都应有来源；样例中的技术栈、分支和层数不是通用事实。
- 缺乏源码或文档时标为概念设计，列出必要假设；不要把设想画成已实现系统。

## architecture：架构图

- **回答的问题：** 系统有哪些边界、层级和组件，各自承担什么责任，协作关系是什么。
- **最少输入：** 主要模块及职责、调用或数据依赖、外部系统、已实现范围；技术名称来自项目证据。
- **布局：** 分层系统可用横向粉彩层框，左侧层名、内部组件卡片；外部服务放独立边界。事件驱动、插件式或端侧系统可改用中心辐射或域分组。
- **关键语义：** 区分逻辑组件、进程、存储和第三方服务；“位于下一层”不自动意味着可直接调用。
- **容易画错：** 为凑层数添加不存在的网关、缓存或消息队列；把配置中的依赖画成业务已接入；把所有外部服务接到同一层。
- **检查：** 每条连线有真实调用者与被调用者；中间件用途明确；可选能力有标签；架构视图与部署视图没有混淆。

可加 1–2 个机制小窗，但只讲有证据的技术重点。多个独立机制优先分图，保留主架构的阅读顺序。

## sequence：时序图

- **回答的问题：** 一次操作如何跨参与者执行，何时返回、等待、重试、推送或结束。
- **最少输入：** 参与者、消息发送者与接收者、先后顺序、同步/异步方式、条件分支、循环与数据写入时机。
- **布局：** 参与者从左到右，生命线垂直向下表示时间；用淡色阶段背景和小图标辅助阅读。参与者较多时采用横版或拆成主链路与细节图。
- **关键语义：** 调用、返回、回调、事件发布分别标明；每个箭头端点锚定真实参与者生命线。激活条表达执行区间，不装饰性铺满。
- **容易画错：** 箭头停在两个参与者之间；把 SSE/订阅事件当作一次普通返回；把后台任务的完成误画为 HTTP 请求立即完成。
- **检查：** 沿每条生命线逐行追踪，核实谁发送、谁接收、何时发生；跨阶段的消息与结束条件能闭合。

细化规则：

1. 项目确有初始化写库、阶段检查点或最终结果保存时，区分这些已有动作，除非源码证明它们是同一动作；没有的存储行为不新增。
2. `alt` 标注互斥分支条件，`opt` 标注可选路径，`loop` 标注循环条件、上限或退出事件。
3. 审核失败后可能重写、补检索、终止或输出当前结果；不能凭经验捏造“每次修改后必复审”。
4. 回调发起者通常是完成工作的服务；事件流须区分事件产生者、队列/通道和订阅者。
5. 取消请求与正常完成可能竞争；只在项目存在时展示确认、清理或最终通知，不擅自承诺立即终止。

## flowchart：流程图

- **回答的问题：** 某项任务按什么步骤和判断推进；适合业务流程、算法控制流和 CI/CD。
- **最少输入：** 起点、输入、步骤、判断条件、分支目标、成功/失败终点；算法另需循环条件，CI/CD 另需触发事件与关卡。
- **布局：** 主路径自上而下或自左向右；条件节点为菱形；按职责可使用泳道，按阶段可使用浅色区域。
- **关键语义：** 边表示控制推进；判断出口写条件。并行、合流、重试与返回各有明确规则。
- **容易画错：** 用操作名代替判断条件；失败路径没有落点；把并发分支排成串行；将手动部署关卡省略成自动发布。
- **检查：** 每条分支可达且有结束或回路条件；算法初始化与更新齐全；CI/CD 的构建、测试、制品与部署顺序有依据。

仅解释代码片段时聚焦该片段；不要自动补出完整产品交付流程。复杂算法可把数据结构示意作为旁注。

## dataflow：数据流图

- **回答的问题：** 数据怎样采集、变换、存储、检索和输出；适合 ETL、日志、RAG 与流式处理。
- **最少输入：** 来源、数据形态、变换步骤、存储位置、消费者、批处理/流式方式及更新触发条件。
- **布局：** 按数据生命周期排成管线；离线准备与在线请求分区；共享存储置于两条链路之间。
- **关键语义：** 连线标数据或事件名称，而非仅标“下一步”；读取与写入分清方向，标注真实存在的版本或索引边界。
- **容易画错：** 将 ETL 编排依赖当数据传输；把 RAG 入库和查询混成同一实时链路；把向量化画成模型训练。
- **检查：** 每次变换的输入/输出可解释；召回、重排、生成仅保留实际步骤；检索结果、来源引用与最终输出关系明确。

涉及敏感字段只展示结构或脱敏示例；技术链路清晰不需要暴露真实用户记录。

## er：实体关系图

- **回答的问题：** 核心实体如何关联，记录的唯一性与关系约束是什么。
- **最少输入：** 实体或表、关键字段、主键/外键、关系基数、可空性；来源可为迁移、DDL 或明确的数据模型设计。
- **布局：** 实体卡片按业务域分组，字段逐行对齐，关系线尽量不交叉；图标仅用于实体标题。
- **关键语义：** 使用统一的乌鸦脚或其他关系记法并给图例；区分一对一、一对多、多对多及可选关系。
- **容易画错：** 仅因字段同名推断外键；遗漏多对多关联表；把 ORM 便利属性当数据库列；把逻辑关系当数据库强约束。
- **检查：** 主外键一致，基数两端正确，可空性与约束有据；概念模型或物理模型在标题中说明。

浅色手绘风应保留字段可读性；字段过多时展示核心字段并标明省略，不伪造完整数据库结构。

## state：状态图

- **回答的问题：** 一个任务、订单、连接或资源在什么事件下改变状态。
- **最少输入：** 对象边界、状态集合、初始/终止状态、触发事件、守卫条件、转移副作用。
- **布局：** 稳定状态作为节点，主要生命周期横向排列，异常或取消路径放下方；复合状态按需嵌套。
- **关键语义：** 状态是持续条件，边是事件或迁移；可采用“事件 [条件] / 动作”标签。
- **容易画错：** 把函数步骤当状态；把“发送通知”这种动作单独当持久状态；遗漏终态、重入或合法回退条件。
- **检查：** 每条迁移能在状态更新逻辑中找到依据；互斥状态不同时成立；超时、取消和恢复行为只画已知部分。

若实际是多字段共同决定状态，注明抽象口径；不要凭单个枚举宣称所有业务状态都已覆盖。

## deployment：部署图

- **回答的问题：** 哪些进程或服务运行在什么节点、环境和网络边界中，如何连通。
- **最少输入：** 运行单元、主机/容器/集群关系、环境、入口、端口或协议、存储与外部依赖。
- **布局：** 用嵌套框表示云/机房、网络、节点与容器边界；外部访问从清晰的入口进入。
- **关键语义：** 区分部署实例与逻辑服务；副本数、持久卷、负载均衡和扩缩容只按配置或实测画出。
- **容易画错：** Docker Compose 被画成 Kubernetes；本地开发启动被画成生产全托管；服务有依赖就推断私网连通或高可用。
- **检查：** 配置中的端口映射、卷和服务名可对应；开发/生产视图明确；未暴露端口不被画成公网入口。

网络边界和实例数量有事实意义，不能为了版式对称而补齐。凭据、实际密钥和不必要的内部地址不入图。

## module：模块、依赖或类图

- **回答的问题：** 代码怎样组织，模块职责如何分离，包、接口或类之间依赖什么。
- **最少输入：** 模块边界、公开接口、实际导入/调用关系；类图另需类型、继承、实现、组合或关联证据。
- **布局：** 按包或业务域分组；模块图保留组件级粒度，类图用名称/属性/方法分栏，依赖图可按方向分层。
- **关键语义：** 说明边表示静态导入、运行调用还是类型关系；UML 的继承、实现、组合使用对应箭头规范。
- **容易画错：** 将目录树直接称为依赖图；把调用当继承；把持有引用当生命周期绑定的组合；反转“依赖于”的箭头。
- **检查：** 边的类型与方向一致；循环依赖如实呈现；接口与实现区分；省略低价值细节但不改变核心依赖。

模块依赖图不承担请求时间顺序；需要说明某次调用时另用时序图。

## ai-pipeline：Agent、训练与评测图

- **回答的问题：** 任务怎样由模型、Agent、工具和数据协作完成，能力如何训练或验证。
- **最少输入：** 具体模式及其节点、输入/输出、决策和终止条件；训练需数据与训练方式，评测需数据集、指标定义及评测执行方式。
- **布局：** Agent 协作用职责分区与带条件的调用链；训练用离线管线；评测用被测系统、样本、评分与汇总链路。确有关系时再连接各图。
- **关键语义：** 分清提示词、检索上下文、工具执行、参数训练和模型推理；模型建议调用工具不等于工具已经执行。
- **容易画错：** 将顺序调用多个提示词包装成自治多 Agent；将 LoRA 适配器画成已接入线上；把自评分等同客观效果；把流程描绘为必然收敛。
- **检查：** 反馈边从真实检查节点出发，重试有边界；训练产物、评测对象和上线接口对应；未联调环节明确标注。

训练图区分数据准备、训练、验证与产物；评测图区分离线样本指标与线上业务指标。
没有结果数据时只展示评测设计，不补“提升百分比”；基座对照与微调模型对照要保持任务与评测口径一致。

## ui-flow：页面与交互流程

- **回答的问题：** 用户从哪个入口开始，跨哪些页面或交互状态完成任务。
- **最少输入：** 用户目标、入口、页面或弹窗、触发动作、权限/校验分支、加载/失败/完成状态。
- **布局：** 小型页面草图或组件卡片串联，箭头标按钮或用户动作；不同角色用泳道，异步状态用局部状态组。
- **关键语义：** 区分页面导航、同页状态变化和后台处理；页面中展示的内容须有产品依据，概念设计注明。
- **容易画错：** 编造尚未实现的页面和按钮；把后端完成当作用户已看到结果；省略登录、权限或错误反馈使流程失真。
- **检查：** 每条交互有入口和落点，返回/退出路径合理；草图与真实截图明确区分；页面名称与项目一致。

只有用户明确要“UI 概念图”时才扩展视觉设计；描述现有产品时优先忠实于当前界面。

## metric/comparison：指标与方案对比图

- **回答的问题：** 实测表现随条件如何变化，或多个方案在哪些维度存在差异。
- **最少输入：** 原始数据或可核对的对比事实、单位、样本范围、测试条件、统计口径；对比实验还需基线与一致的评估设置。
- **布局：** 时间变化用折线，类别比较用条形，分布用直方/箱线等合适图型；定性能力比较用矩阵，不伪造分数或雷达面积。
- **关键语义：** 使用绘图工具按真实数据生成坐标、曲线与标签，手绘风只作用于配色与装饰；保留单位、来源和必要误差区间。
- **容易画错：** 让生图模型编造数字；截断坐标夸大差异；混用平均值与分位数；将示例数据标为实测；用不等配置的测试声称性能胜出。
- **检查：** 图中数字可回算到源数据，分母和单位一致；样本量与条件可查；缺失值不替换成零；数据更新后重新绘制。

只有示例数据时醒目标注“示例数据”；没有数据时可交付指标定义或待填模板，不能声称测得提升。
实测图导出可分享文件，并保留生成脚本或数据出处，便于复核；不要用生成式图片重画精确数值部分。
